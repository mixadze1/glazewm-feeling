# Проверка памяти и завершения GlazeWM

Проверено на Windows 20 сентября 2026 года. Исправления находятся в рабочем дереве; тестовая сборка — `target/debug`. Параллельные изменения пользователя не отменялись. После проверки восстановлен запуск из `target/release` с исходными аргументами.

## Исправления

| Область | Причина | Изменение |
| --- | --- | --- |
| Дерево контейнеров | Родители и дети взаимно удерживались сильными `Rc`; удалённое поддерево и завершённое состояние могли оставаться в памяти | Родительские ссылки заменены на `Weak`, обновлены операции attach/wrap/flatten |
| Порядок фокуса | Итератор каждый раз возвращал первого ребёнка; сбор в коллекцию мог бесконечно расходовать память | Итератор продвигается по порядку фокуса и завершается |
| IPC-подписки | Разрыв соединения до обработки подписки терялся; массовые отписки могли выпадать из broadcast-буфера | Отслеживается закрытие ответного канала; отписка непосредственно отменяет зарегистрированную задачу |
| IPC-сервер | Дочерние задачи соединений жили отдельно от задачи accept; очереди запросов и ответов были неограниченными | Соединения принадлежат `JoinSet`; stop отменяет и дожидается задач, закрывает сокеты и незавершённые handshake. Очереди ограничены 256 запросами / 64 ответами; переполненный клиент отключается; запись в сокет ограничена таймаутом |
| Трей | Поток навсегда ожидал глобальный канал событий меню | Добавлены сигнал остановки, ограниченное ожидание и join до остановки платформенного цикла |
| Watcher | Дескриптор дочернего процесса сразу терялся | Главный процесс хранит `Child`, закрывает IPC, ждёт watcher; через 3 секунды завершает зависший дочерний процесс. `kill_on_drop` страхует выход по ошибке |
| Аварийное восстановление | `ShowWindow` не снимал cloak после аварии во время анимации | Watcher также снимает cloak с управляемых окон |
| Win32 event loop | Поставленные в очередь сырые callback-указатели терялись при завершении; окно не уничтожалось, если loop не запускался | Асинхронные callback принадлежат очищаемой очереди; синхронный callback остаётся во владении отправителя; окно уничтожается в Drop; ошибка `GetMessageW` обрабатывается отдельно |
| Оконные хуки | `UnhookWinEvent` вызывался с другого потока; частично созданные хуки терялись при ошибке установки | Удаление выполняется на потоке установки; частичная установка откатывается; sender очищается и допускает повторное создание |
| Клавиатурный хук | Callback сохранялся до успешной регистрации; очистка была асинхронной и неидемпотентной | Callback сохраняется после установки; очистка синхронная на потоке владельца; повторный terminate безопасен |
| Mutex | Дескрипторы терялись при обнаружении уже запущенного приложения и при проверке состояния | Все полученные дескрипторы закрываются; исправлен инвертированный результат `is_running` |
| GDI-регион iris | При отказе `SetWindowRgn` владение не передаётся Windows, а регион не удалялся | Регион освобождается на ветке ошибки |
| `ThreadBound` | Даже на потоке владельца Drop пропускался после остановки dispatcher | На потоке владельца значение уничтожается непосредственно |
| Паника рабочего потока | Главный поток мог остаться в message loop после паники WM | Guard останавливает loop и при раскрутке стека |
| Отложенные эффекты | Задача повторной установки рамки могла отработать после восстановления окон при выходе | При Drop состояния инвалидируется поколение отложенных обновлений |

Удаление WinEvent-хуков на потоке установки соответствует [документации Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-unhookwinevent). Передача владения регионом только при успешном вызове описана в [SetWindowRgn](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowrgn).

## Проверки

- `build-local.ps1 -Test`: сборка workspace успешна; **117 тестов прошли**, падений нет. В это число включены doctest; 16 существующих тестов помечены ignored.
- Добавлены 14 регрессионных тестов: освобождение дерева и поддерева, слабый родитель, конечность итератора, поздняя подписка после отключения, 100 массовых отписок, медленный подписчик, закрытие сокетов и handshake, освобождение callback/скрытого окна, повторное создание оконных и клавиатурных хуков, остановка при панике, отмена отложенных рамок и освобождение ThreadBound после остановки loop.
- `cargo clippy --locked --workspace --all-targets`: успешно, без ошибок. В проекте остаются предупреждения вне исправленной логики.
- `git diff --check`: успешно.

## Проверка настоящих процессов

Использована отдельная копия debug-бинарников в `target/memory-audit/bin`. В тестовом конфиге отключены пользовательские startup/shutdown-команды и управление существующими окнами. Перед испытанием текущий GlazeWM завершён штатно; после испытания исходный запуск восстановлен.

В окончательном прогоне выполнены 720 WebSocket-подключений с подпиской и принудительным разрывом клиентского соединения. В каждом цикле первые 30 подключений служили прогревом, затем сравнивались ресурсы после следующих 150.

| Цикл | Способ остановки | Главный процесс + watcher завершились за | Осталось тестовых процессов | Изменение private bytes | Изменение handles / threads |
| --- | --- | ---: | ---: | ---: | ---: |
| 1 | `wm-exit` | 146 мс | 0 | −64 KiB | 0 / 0 |
| 2 | `wm-exit` | 100 мс | 0 | +88 KiB | 0 / 0 |
| 3 | `wm-exit` | 99 мс | 0 | −124 KiB | 0 / 0 |
| 4 | Принудительное завершение главного процесса | 8 мс | 0 | +32 KiB | +2 / 0 |

Штатные CLI-команды завершились успешно. После принудительного завершения WM watcher вышел самостоятельно. Неограниченного роста памяти в этой нагрузке не наблюдалось; небольшие колебания счётчиков не являются доказательством утечки или её полного отсутствия.

Артефакты локального прогона: `target/memory-audit/results.json`, `smoke.log`, `build.log`, `clippy.log`, конфиг и сценарий `smoke.ps1`. Каталог `target` не отслеживается Git.

## Границы проверки

Проверка выполнения ориентирована на Windows. macOS не собиралась и не профилировалась. Длительный многочасовой прогон GPU-анимаций и ручное нажатие Exit в меню трея не выполнялись; общий путь очистки проверялся реальным `wm-exit`, а освобождение дерева и платформенных ресурсов — регрессионными тестами. Тестовый конфиг игнорировал существующие окна, поэтому восстановление cloak после аварии не проверялось визуально.

Доказать отсутствие всех утечек этими проверками нельзя; перечисленные дефекты исправлены, а проверенные сценарии завершения не оставляют тестовых процессов.
